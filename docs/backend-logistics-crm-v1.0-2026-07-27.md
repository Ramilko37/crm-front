# 1. Общие положения

## 1.1. Цель и границы

Цель доработки - сделать ежедневную работу логистов и менеджеров предсказуемой, исключить потерю данных и технические поля из пользовательского интерфейса, а также не допускать физически невозможного включения заказов в рейсы.

В объём документа входят: Заказы, редактирование через чат, Заявки, Компании, Путевые точки, Фабрики и Пользователи.

Документ описывает пользовательское поведение, бизнес-правила и критерии приёмки; конкретная архитектура и выбор внешних сервисов определяются командой разработки после уточнений.

Требования к рейсам описаны только в части связи с путевыми точками и допустимости добавления заказа.

## 1.2. Термины

| Термин | Определение |
| --- | --- |
| Заявка | Предварительный запрос на закупку товара до подтверждения и перехода к логистическому исполнению. |
| Заказ | Подтверждённая логистическая сущность, которая может проходить маршрут и включаться в рейс. |
| Рейс | Транспортное перемещение с заданной последовательностью путевых точек и ограничениями по весу/объёму. |
| Путевая точка | Фактическое или плановое место прохождения рейса и контроля физического местоположения товара. |
| Адрес погрузки | Конкретная активная точка фабрики, с которой может быть выполнена погрузка товара. |
| Черновик | Незавершённый заказ, данные которого сохраняются до окончательного создания заказа. |

## 1.3. Приоритеты и типы задач

| Приоритет | Смысл |
| --- | --- |
| Critical | Блокирует ключевой процесс или создаёт риск потери/искажения данных. |
| High | Существенно влияет на рабочий процесс; требуется в ближайшем релизе. |
| Medium | Улучшает удобство и управляемость; допускается планирование после High. |
| Low | Косметическая или второстепенная доработка. |

| Тип | Смысл |
| --- | --- |
| Bug | Исправление поведения, которое уже должно работать, но работает некорректно. |
| Functional requirement | Новая или уточнённая бизнес-функция. |
| Validation | Проверка заполнения, формата или допустимости данных. |
| Improvement | Улучшение UX/UI или рабочего сценария. |
| Testing | Функциональное или регрессионное тестирование существующего поведения. |

## 1.4. Общие требования к интерфейсу

Не показывать пользователю(клиенту) внутренние идентификаторы сущностей (Company ID, Country ID, Factory ID и аналогичные); отображать понятные названия.

Для длинных справочников использовать автодополнение и поиск с первых введённых символов.

Названия стран по умолчанию отображать на английском языке.

Ошибки должны содержать конкретную причину и не должны приводить к очистке введённых данных.

Создание связанных сущностей внутри формы не должно перезапускать текущий сценарий и должно сразу выбирать созданную запись.

Списки и фильтры должны обновляться без полной перезагрузки страницы.

Кнопки «Применить» и «Сбросить» размещать единообразно; «Применить» является основной кнопкой.

# 2. Заказы

## 2.1. Создание нового заказа

### ORD-CRE-01. Создание новой компании из заказа

**Тип: Bug    |    Приоритет: High**

Текущее состояние. После ввода данных форма сбрасывается, компания не создаётся или не появляется в списке.

Требуемое поведение

Сохранять новую компанию в базе данных только после успешной валидации.

После успешного сохранения автоматически выбирать компанию в текущем заказе.

Добавлять компанию в общий справочник для последующих заказов.

Не очищать форму до подтверждения успешного сохранения; при ошибке сохранять введённые значения.

Критерии приёмки

Пользователь создаёт компанию внутри мастера заказа без перезагрузки страницы.

Созданная компания сразу выбрана и доступна в следующих заказах.

При серверной или валидационной ошибке введённые данные не пропадают.

### ORD-CRE-02. Справочник стран и автодополнение

**Тип: Improvement    |    Приоритет: Medium**

Требуемое поведение

Отображать страны на английском языке (например, Italy, Germany, France).

Фильтровать варианты с первых введённых символов без необходимости прокручивать весь список.

Использовать один и тот же справочник стран во всех модулях CRM.

Критерии приёмки

Ввод «It» предлагает Italy, ввод «Ger» предлагает Germany.

В пользовательском интерфейсе не отображается Country ID.

### ORD-CRE-03. Создание новой фабрики из заказа

**Тип: Bug    |    Приоритет: High**

Текущее состояние. Новая фабрика не сохраняется либо форма работает нестабильно.

Требуемое поведение

Сохранять фабрику в базе данных.

После сохранения автоматически подставлять фабрику в текущий заказ.

Добавлять фабрику в общий справочник и не перезапускать мастер заказа.

Критерии приёмки

Фабрика создаётся без перезагрузки страницы и сразу выбирается в текущем заказе.

Введённые ранее данные заказа сохраняются.

### ORD-CRE-04. Почтовый индекс и определение города

**Тип: Functional requirement / Validation    |    Приоритет: High**

Требуемое поведение

Сделать почтовый индекс обязательным полем.

Определять город после ввода или выбора корректного индекса с учётом выбранной страны.

Если индексу соответствует несколько населённых пунктов, показывать список вариантов.

Разрешить ручную корректировку города, если автоматический вариант неверен.

Критерии приёмки

После ввода индекса город заполняется автоматически либо предлагается выбор из подходящих вариантов.

Без индекса переход к следующему шагу невозможен; данные формы при этом сохраняются.

Примечание. До реализации необходимо выбрать источник справочника индексов: локальная база, внешний API или внутренний справочник CRM.

### ORD-CRE-05. Обязательные поля и валидация

**Тип: Validation    |    Приоритет: High**

Требуемое поведение

Обязательные поля: почтовый индекс, номер инвойса, сумма инвойса, заявленный объём и заявленный вес.

Не разрешать сохранение/переход далее при незаполненных обязательных полях.

Визуально выделять поле и показывать понятное сообщение об ошибке.

Сумма, вес и объём принимают только положительные числовые значения.

Для суммы указывать валюту; для веса и объёма - единицы измерения.

Критерии приёмки

Заказ не создаётся при отсутствии любого обязательного значения.

После ошибки валидации все корректно введённые значения остаются на месте.

Невалидные числовые значения отклоняются с указанием причины.

### ORD-CRE-06. Товары и описание груза

**Тип: Functional requirement    |    Приоритет: Medium**

Требуемое поведение

Предусмотреть поля «Товары» и «Описание груза».

Минимально обеспечить одно текстовое описание груза.

При выборе детализированной модели поддержать позиции: наименование, описание, количество, вес, объём, стоимость и примечание.

Критерии приёмки

Описание груза сохраняется и отображается в карточке заказа.

Если включена позиционная модель, можно добавить несколько товарных строк без потери данных.

Примечание. Необходимо подтвердить, требуется ли полноценная табличная детализация товаров или достаточно обязательного текстового описания.

### ORD-DOC-01. Массовая загрузка и классификация документов

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

Добавить область Drag & Drop и стандартный выбор нескольких файлов.

Показывать список файлов; разрешить удаление, переименование и добавление комментария.

Для каждого файла хранить тип документа; разрешить назначить один тип группе выбранных файлов или отдельный тип каждому файлу.

Разрешить менять тип документа после сохранения.

Минимальные типы: Invoice, Packing List, Proforma Invoice, CMR, Export Declaration, Customs Declaration, Certificate of Origin, Transport Document, Contract, Specification, Photo, Other.

Администратор должен иметь возможность расширять справочник типов документов.

Показывать имя, размер, дату загрузки, автора и прогресс загрузки.

Предупреждать о повторной загрузке того же файла.

Ошибка одного файла не должна удалять остальные успешно выбранные или загруженные файлы.

Документы не должны пропадать при переходе между шагами и должны входить в черновик.

Критерии приёмки

Пользователь перетаскивает несколько файлов и видит отдельный статус каждого.

Каждому файлу можно назначить и изменить тип; массовое назначение работает для выбранной группы.

После навигации между шагами и восстановления черновика список документов сохраняется.

### ORD-DRF-01. Сохранение данных между шагами

**Тип: Bug    |    Приоритет: Critical**

Текущее состояние. При возврате с шага «Фабрика» на ранее заполненный шаг введённые данные пропадают.

Требуемое поведение

Сохранять все значения при переходе вперёд, назад и открытии ранее пройденного шага.

Не очищать данные при ошибке валидации, создании компании/фабрики или загрузке документов.

Кнопка «Назад» должна возвращать на предыдущий шаг без сброса формы.

Критерии приёмки

Пользователь заполняет второй шаг, переходит на пятый и возвращается: значения остаются без изменений.

Ни один из проверяемых сценариев навигации и ошибок не приводит к потере данных.

### ORD-DRF-02. Автосохранение черновика

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

Автоматически сохранять незавершённый заказ в статусе «Черновик».

Показывать состояния «Сохранение...», «Сохранено», «Ошибка сохранения».

При случайном закрытии формы предлагать восстановить черновик.

После окончательного создания переносить все данные и документы черновика в карточку заказа.

Критерии приёмки

После повторного открытия пользователь может восстановить незавершённый заказ.

Индикатор соответствует фактическому результату сохранения на сервере.

После создания заказа черновые данные и документы присутствуют в карточке без дублей.

Примечание. Интервал автосохранения, срок хранения и правила удаления черновиков требуют отдельного согласования.

### ORD-FLT-01. Компактная группировка фильтров

**Тип: Improvement    |    Приоритет: High**

Требуемое поведение

Сгруппировать поля по блокам, указанным выше.

Использовать одинаковые размеры полей и единые отступы без наложений.

Сделать панель компактной и пригодной для ежедневной работы.

Критерии приёмки

Все группы и поля доступны и корректно отображаются на стандартном рабочем разрешении.

Фильтры можно комбинировать без визуальных конфликтов.

### ORD-FLT-02. Понятные названия и автодополнение

**Тип: Improvement    |    Приоритет: High**

Требуемое поведение

Вместо Client ID, Company ID, Factory ID и других внутренних ID показывать названия сущностей.

Для клиента, компании, экспедитора, фабрики, рейса, страны и типов документов использовать поиск с автодополнением.

Критерии приёмки

Пользователь выбирает сущность по названию и не видит технический ID.

Поиск сокращает список с первых введённых символов.

### ORD-FLT-03. Сворачивание и запоминание состояния

**Тип: Improvement    |    Приоритет: Medium**

Требуемое поведение

По умолчанию показывать панель фильтров свёрнутой.

Раскрывать её по кнопке «Показать фильтры».

Запоминать последнее состояние панели для текущего пользователя.

Критерии приёмки

# 6. Путевые точки

## 6.1. Назначение и модель

Ключевой принцип. Заказ можно добавить в рейс только тогда, когда товар физически находится в точке, которую рейс ещё не прошёл или в которой рейс находится сейчас. Это исключает «фантомные» заказы и требует дополнительного подтверждения логистом.

### WPT-CRE-01. Создание путевой точки

**Тип: Functional requirement    |    Приоритет: High**

Текущее состояние. В разделе отсутствует кнопка создания.

Требуемое поведение

Добавить кнопку «Создать путевую точку» над списком.

Поля: наименование, тип, страна, город, индекс, адрес, связанная компания, координаты (при наличии), контактное лицо, телефон, e-mail, комментарий, активность.

Типы как минимум: Factory, Forwarder warehouse, Consolidation warehouse, Customs warehouse, Terminal, Loading point, Unloading point, Border crossing, Customs office, Transit point, Other.

Справочник типов должен редактироваться администратором.

Критерии приёмки

Путевая точка сохраняется и сразу появляется в списке.

Неактивная точка не предлагается в новых маршрутах, если иное не разрешено администратором.

### WPT-FLT-01. Исправление и состав фильтров

**Тип: Bug / Improvement    |    Приоритет: High**

Текущее состояние. Блок фильтров отображается некорректно.

Требуемое поведение

Выровнять поля, убрать наложения и обеспечить корректное отображение на стандартных экранах, планшетах и небольших разрешениях.

Добавить сворачивание/раскрытие.

Фильтры: наименование, тип, страна, город, компания, статус, наличие активных рейсов, дата создания.

Для страны, города и компании использовать автодополнение; разрешить комбинации фильтров.

Добавить кнопки «Применить» и «Сбросить».

Критерии приёмки

Панель не содержит визуальных наложений на поддерживаемых разрешениях.

Комбинированные фильтры возвращают корректные точки; сброс возвращает полный список.

## 6.2. Местоположение заказа

### WPT-ORD-01. Текущее местоположение и статус товара

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

Хранить текущую путевую точку заказа.

Хранить дату/время поступления и выбытия, подтверждающего пользователя, документ или комментарий.

Поддержать статусы: ожидается, прибыл, подтверждён на складе, готов к погрузке, загружен, выбыл, отменён.

Критерии приёмки

Карточка заказа показывает актуальную точку, статус и подтверждение.

Изменение местоположения создаёт запись истории движения.

## 6.3. Маршрут рейса

### WPT-TRIP-01. Последовательность точек рейса

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

Задавать маршрут как упорядоченную последовательность путевых точек.

Для каждой точки хранить порядок, плановые и фактические даты прибытия/отправления и статус прохождения.

Поддержать статусы: запланирована, рейс следует к точке, рейс прибыл, погрузка, выгрузка, рейс покинул точку, пропущена, отменена.

Критерии приёмки

Маршрут однозначно показывает уже пройденные, текущую и будущие точки.

Изменение фактического статуса влияет на проверку допустимости добавления заказа.

## 6.4. Добавление заказа в рейс

### WPT-CHK-01. Автоматическая проверка допустимости

**Тип: Functional requirement    |    Приоритет: Critical**

Требуемое поведение

Текущая точка заказа должна присутствовать в маршруте рейса.

Рейс не должен уже покинуть эту точку.

Нахождение заказа в точке должно быть подтверждено.

Статус заказа должен допускать погрузку.

Заказ не должен быть назначен в другой активный рейс.

Вес и объём не должны превышать доступную вместимость рейса.

После автоматических проверок добавление подтверждает логист.

Критерии приёмки

Заказ в текущей или будущей точке маршрута можно добавить при выполнении всех условий.

Заказ нельзя добавить после того, как рейс покинул точку его фактического нахождения.

Проверка выполняется на сервере, а не только визуально в интерфейсе.

### WPT-CHK-02. Запрещающие условия и объяснение отказа

**Тип: Functional requirement    |    Приоритет: Critical**

Требуемое поведение

Запрещать добавление, если рейс прошёл точку, товар находится в другой точке, нахождение не подтверждено, заказ уже в другом активном рейсе, заказ отменён, рейс завершён либо превышены вес/объём.

Вместо общей ошибки показывать конкретную причину с номером рейса/названием точки, где это уместно.

Примеры: «Рейс уже покинул Milan», «Местоположение заказа не входит в маршрут», «Нахождение товара не подтверждено», «Недостаточно доступного объёма».

Критерии приёмки

Для каждого запрещающего условия есть отдельный тест и понятное сообщение.

После отказа заказ и рейс остаются в исходном непротиворечивом состоянии.

### WPT-CFM-01. Ручное подтверждение логистом

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

Перед подтверждением показывать номер заказа, текущую точку, рейс, точку погрузки, вес, объём и остаток вместимости рейса.

Действия: «Подтвердить добавление» и «Отмена».

Критерии приёмки

Без явного подтверждения логиста заказ не включается в рейс.

После подтверждения остаток веса и объёма пересчитывается.

### WPT-OVR-01. Принудительное добавление с особыми правами

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

Разрешать обход проверки только пользователю со специальным правом.

Обязательно запрашивать причину и записывать пользователя, дату и время.

Визуально отмечать заказ как добавленный с обходом проверки.

Критерии приёмки

Обычный логист не может выполнить обход.

Администратор/уполномоченный пользователь вводит причину, после чего действие полностью отражается в журнале.

### WPT-HIS-01. История движения заказа

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

Показывать дату/время, путевую точку, событие, пользователя и комментарий.

Автоматически добавлять события прибытия, подтверждения, погрузки, выбытия и включения в рейс.

Не разрешать обычному пользователю редактировать историю задним числом.

Критерии приёмки

История воспроизводит последовательность движения товара.

Попытка изменить прошлую запись без специальных прав отклоняется.

## 6.5. Итоговая приёмка путевых точек

Создание и фильтрация путевых точек работают; интерфейс не имеет визуальных дефектов.

В заказе хранится подтверждённое физическое местоположение, а в рейсе - упорядоченный маршрут.

Система запрещает физически невозможное добавление и сообщает точную причину.

Обычное добавление подтверждает логист; обход доступен только специальной роли и полностью журналируется.

История движения неизменяема обычным пользователем и отражает ключевые события.

Разместить заметный блок «Адреса погрузки» прямо в форме фабрики.

Поддержать несколько активных адресов: название точки, страна, индекс, город, адрес, контактное лицо, телефон, e-mail, часы работы, комментарий, основной адрес, активность.

При создании предложить переключатель «Использовать основной адрес фабрики как основной адрес погрузки».

Добавить кнопку «Добавить ещё один адрес погрузки».

При редактировании разрешить добавлять, изменять и деактивировать адреса.

Адрес, использованный в заказах, не удалять физически; переводить в неактивный статус для сохранения истории.

Критерии приёмки

У одной фабрики можно сохранить несколько адресов и отметить один основным.

Неактивный адрес сохраняется в старых заказах, но недоступен в новых.

Адреса видны без перехода в абстрактный раздел «Ресурсы».

### FAC-ORD-01. Выбор адреса погрузки в заказе

**Тип: Functional requirement    |    Приоритет: High**

Требуемое поведение

После выбора фабрики показывать поле «Адрес погрузки».

Автоматически подставлять основной активный адрес и разрешать выбрать другой активный.

Не использовать юридический адрес автоматически, если он не помечен как адрес погрузки.

Критерии приёмки

Основной адрес выбирается автоматически.

Пользователь может выбрать другой активный адрес; неактивные адреса не предлагаются.

### FAC-RES-01. Раздел «Ресурсы»

**Тип: Improvement    |    Приоритет: Medium**

Требуемое поведение

Определить фактический состав раздела и его бизнес-назначение.

Если внутри только адреса - перенести их в карточку фабрики и переименовать раздел в «Адреса погрузки».

Если внутри адреса и контакты - использовать название «Адреса и контакты».

Если отдельной бизнес-логики нет - удалить лишний уровень навигации.

Критерии приёмки

Название раздела однозначно описывает содержимое.

Ключевые адреса погрузки доступны непосредственно в создании и редактировании фабрики.

Примечание. Окончательное решение зависит от проверки текущего содержимого кнопки «Ресурсы».

### FAC-FLT-01. Проверка фильтров фабрик

**Тип: Testing    |    Приоритет: Medium**

Текущее состояние. По пользовательской оценке существенных изменений не требуется.

Требуемое поведение

Проверить отображение и работу фильтров по названию, стране, городу и статусу.

Критерии приёмки

Все четыре фильтра работают отдельно и в комбинации, а сброс возвращает полный список.

### USR-FLT-01. Компактный двухуровневый интерфейс

**Тип: Improvement    |    Приоритет: High**

Требуемое поведение

В первой строке разместить поиск, компанию, роль и статус.

Во второй строке разместить страну, город, последний вход и наличие e-mail.

Использовать единые размеры полей, отступы и адаптивное переносимое расположение.

Критерии приёмки

Основные сценарии поиска доступны без прокрутки длинной формы.

На поддерживаемых разрешениях элементы не накладываются и сохраняют читаемость.

### USR-FLT-02. Понятные поля вместо технических ID

**Тип: Improvement    |    Приоритет: High**

Требуемое поведение

Убрать Company ID и другие внутренние идентификаторы.

В поле «Компания» показывать названия с автопоиском.

Глобальный поиск должен также находить пользователя по компании.

Критерии приёмки

Пользователь выполняет поиск и фильтрацию, не видя внутренних ID.

### USR-FLT-03. Быстрые фильтры

**Тип: Improvement    |    Приоритет: Medium**

Требуемое поведение

Добавить быстрые переключатели: Только активные, Только логисты, Только менеджеры, Без компании.

Показывать активное состояние каждого переключателя и разрешать сброс.

Критерии приёмки

Каждый переключатель применяет ожидаемый критерий одним действием и корректно комбинируется с основной формой.

### USR-FLT-04. Применение, сброс и единый стиль

**Тип: Improvement    |    Приоритет: Medium**

Требуемое поведение

Разместить справа кнопки «Сбросить» и «Применить»; «Применить» - основная.

Применять единые принципы фильтров во всех разделах CRM: глобальный поиск, смысловые группы, названия вместо ID, автодополнение и одинаковое расположение действий.

Критерии приёмки

Применение обновляет список без полной перезагрузки.

Сброс очищает поля и быстрые переключатели.

Поведение совпадает с фильтрами в разделах Заказы и Компании.

# 9. Сквозные сценарии приёмки

Ниже приведены обязательные end-to-end сценарии. Они дополняют локальные критерии требований и используются для итоговой регрессии.

| ID | Сценарий |
| --- | --- |
| E2E-01 | Создать заказ, внутри него создать компанию и фабрику, заполнить обязательные поля, вернуться между шагами и завершить заказ без потери данных. |
| E2E-02 | Загрузить несколько документов, массово и индивидуально назначить типы, восстановить черновик и убедиться, что файлы сохранены без дублей. |
| E2E-03 | Найти заказ глобальным поиском и отфильтровать список по нескольким смысловым группам; сохранить и повторно применить набор фильтров. |
| E2E-04 | Изменить заказ через чат и убедиться, что карточка и журнал изменений обновились без перезагрузки и дублей. |
| E2E-05 | Создать заявку, подтвердить её, конвертировать в заказ и проверить перенос данных и двустороннюю связь. |
| E2E-06 | Создать компанию, затем найти её по стране, городу, роли и глобальному поиску. |
| E2E-07 | Создать маршрут рейса; успешно добавить заказ из будущей точки; запретить заказ из уже пройденной точки с понятной причиной. |
| E2E-08 | Создать фабрику с несколькими адресами, выбрать основной и альтернативный адрес в заказах; деактивировать использованный адрес без нарушения истории. |
| E2E-09 | Отфильтровать пользователей по компании, роли, статусу, последнему входу и быстрому фильтру; затем полностью сбросить условия. |

## 9.1. Общий Definition of Done

Все критерии приёмки соответствующего релиза выполнены и подтверждены QA.

Исправленные сценарии покрыты регрессионными тестами; критические бизнес-проверки выполняются на сервере.

Нет потери данных при ошибках, навигации, повторном сохранении и восстановлении черновика.

Пользовательский интерфейс не показывает технические ID и выдаёт конкретные сообщения об ошибках.

Журналирование предусмотрено для изменений заказа, движения товара и обхода логистических ограничений.

Справочники, роли, статусы и миграция существующих данных согласованы до выпуска в продуктивную среду.

## 10.1. Рекомендуемый порядок реализации

Сначала устранить Critical: потеря данных между шагами и некорректное включение заказов в рейс.

Затем закрыть High в создании заказа, документах, компаниях, путевых точках, фабриках и чат-редактировании.

После стабилизации реализовать Medium UX-улучшения: сохранённые фильтры, пресеты, быстрые фильтры и переименование разделов.

Каждый этап завершать сквозной регрессией по сценариям раздела 9.
